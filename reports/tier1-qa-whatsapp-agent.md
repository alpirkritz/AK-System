## Post-review fixes (found during Alpir's first live runs, 2026-09-30)

1. **Wrong Notion account label.** `TIER1_QA_NOTION_ACCOUNT_LABEL` was `alpir-daz` (a misunderstanding of a descriptive phrase, not a real config value) — the real `NOTION_ACCOUNTS` label is `DAZ`. Fixed.
2. **`Insufficient permissions` (403) on the Comments API.** Not a code bug — the `DAZ` Notion integration needs its "Read comments" capability enabled in Notion's own integration settings. This is exactly the hard safety rule working as designed (it correctly refused to send a partial update).
3. **"Unexpected token '<' ... is not valid JSON" on manual "הרץ עכשיו".** Root cause: the original `notion-tier1-qa.ts` fetched every test's and every linked task's body text + comments **fully sequentially** (one Notion HTTP call at a time). For a real-sized database this is slow enough that the manual trigger — which goes through the public tunnel from the browser, unlike the cron path, which hits the app directly on the EC2 box — could run long enough to have its response replaced by the host/tunnel's own HTML error page, which tRPC's client can't parse. Fixed by parallelizing the fetch with a small concurrency cap (`mapWithConcurrency`, limit 3, respecting Notion's ~3 req/s guidance) and adding `export const maxDuration = 300` to the tRPC route (matching the cron routes) as a secondary safety net.
4. **`UNIQUE constraint failed: tier1_qa_snapshots.snapshot_date`** on a same-day re-run (expected during Alpir's own testing — multiple manual runs on the same calendar day). `saveSnapshot` did a plain `insert`; changed to an upsert (select by `snapshotDate`, update if found, insert otherwise), matching the select-then-branch pattern already used elsewhere in the codebase (e.g. `upsertInPageMeetingNote`).

5. **Deploy didn't pick up new env vars.** `docker compose up -d --build` does not recreate a container when only a referenced `env_file`'s contents changed, so `TIER1_QA_WHATSAPP_GROUP_JID` / `WHATSAPP_ALLOWED_GROUP_JIDS` sat in the scp'd files while both containers kept their old environment. `scripts/deploy-ec2.sh` now passes `--force-recreate`.
6. **Delivery failures were invisible.** The delivery diagnostic was appended only to the push text, which `excerpt()` truncates to 240 chars, and `/agents/manage` renders `lastRunError` only when status is `'error'`. Now the status line is part of the saved report text, and a failed group send marks the run `'error'` with the concrete reason.
7. **`not-acceptable` (WhatsApp 406) on every group send — the actual root cause.** The bridge's `^6.7.18` range resolved to `@whiskeysockets/baileys@6.17.16`, a mis-versioned npm publish whose `lib/` is byte-identical to the old `6.7.16` (verified with `diff -rq` against the 6.7.16 tarball). That code predates WhatsApp's LID addressing: for a modern group it fetches participants as `@lid` ids, then sends them in a USync `<user jid="…@lid">` node, which the server rejects with `not-acceptable`. Self-chat never touched that path, which is why 1:1 sends kept working. Fix: pin **`6.7.24`** (npm `legacy` tag — last 6.x, LID-aware group sends with `addressing_mode`). 6.7.18+ removed `makeInMemoryStore`, so `whatsapp-client.ts` now has a ~30-line local store covering the two things we used it for (contact `lid`→phone mapping for DM capture, per-chat last-message time for group discovery), plus a `cachedGroupMetadata` hook. `sendWhatsAppGroupMessage` also preflights `groupMetadata()` so a wrong JID / community parent / admins-only group fails with a human-readable reason instead of a bare 406. Verified: `tsc --noEmit` clean, `config.test.ts` 6/6, `pnpm install --frozen-lockfile` clean for the whole workspace with the regenerated lockfile (which also absorbs pre-existing, uncommitted `apps/mobile/package.json` drift — not this change's doing, but it had to be resolved for the lockfile to be frozen-valid again).

8. **Message template didn't match the spec's own binding example.** The spec had two message specs: Appendix A §10 (verbose, per-item, with links — from the raw prompt) and a "Target output style" example further down (compact dashboard, no links) that the spec text itself labeled "binding tone/format bar." Implementation followed §10 literally and missed the reconciliation — Alpir confirmed on live output that the compact example was what he actually wanted. Rewrote `A_Agents/10_tier1_qa_reporter.md`'s template to match the compact style: status-breakdown bullets with emoji, `---` dividers, a name-only "ממתינות לאור" list, bugs grouped by linked test/street instead of listed flat, no links anywhere, target ~120–250 words (down from 300–600). Added `linkedTestIds`/`linkedBugIds` back into `buildGroundingPayload()`'s trimmed payload (they existed on the full records already, just weren't passed through) so the narration step can actually do the street-grouping. No code-side numeric logic changed — this is a narration-template and grounding-payload-shape fix only; `notion-tier1-qa.test.ts` still passes unchanged.

9. **Repo edits to an existing agent card never reached production.** Production reads agent cards from the `abc-data` volume (`ABC_ROOT=/data/abc`), seeded by `scripts/production-start.sh` with `cp -an` (no-clobber) so UI edits survive redeploys — which also meant a repo change to a file already on the volume was silently dropped. That's why the rewritten template in fix 8 didn't show up: the volume still had the first-deploy `10_tier1_qa_reporter.md`. Replaced the seeder with a per-file `.seed-manifest` (sha256 of what was last seeded): new file → copy; identical → skip; unchanged since last seed → safe to overwrite with the repo version; differs from both → UI-edited, keep + warn; `ABC_SEED_FORCE_FILES` (comma list) → overwrite regardless. Tested all four paths locally. Because the live volume predates the manifest, `deploy/production.env` carries a one-shot `ABC_SEED_FORCE_FILES` for the two Tier 1 files — **Alpir should delete that line after the next deploy**, or future UI edits to those files get reverted every deploy. Other pre-existing files that already differ from the image will be listed as "kept UI-edited" in the container log on first boot, which doubles as an audit of what's been changed in the UI.

## Change: Ready for QA routing (2026-10-05)

Spec updated first (two new acceptance criteria), then implemented:

- `detectGaps`: an open bug with Status matching `/ready[\s_-]*for[\s_-]*qa/i` emits a `ready_for_qa` gap whose `people` are the ticket's QA names, else Reporter names, else empty — with `peopleSource: 'qa' | 'reporter'`.
- `routeOwner`: `ready_for_qa` → new bucket `לבעלים מהטיקט` when `people` is non-empty, else `נדרש לקבוע בעלים`. `ownerActions` carry `people`/`peopleSource` through.
- `buildGroundingPayload`: bugs now include `qa` and `reporter`, so future wording-only rules about those fields can go in the agent card without a code change. Ownership still comes only from `ownerActions`.
- Agent card: "הצעדים להיום" renders ticket owners as `@<name>` (merged into the אור/דור line when it's one of them; "(אין QA בטיקט)" when it fell back to Reporter), with an explicit rule not to re-derive owners from `qa`/`reporter`/`assignee`.
- Tests: 6 new (QA wins over Reporter; Reporter fallback; neither → unassigned; status spelling variants; no fire for other statuses or non-open bugs; payload exposes qa/reporter without leaking body text). `notion-tier1-qa.test.ts` 31/31, `tsc --noEmit` clean for the service.

Design note, for whoever asks "why isn't this rule in the agent .md?": the card is an LLM prompt, so anything there is best-effort. Rules that decide *who owns what* or *what a number is* live in code; the card owns wording and layout.

## Fix: Ready for QA ownership wasn't rendering in live output (2026-10-05)

First live message after the restore showed the compact template correctly, including bugs whose Notion status is literally "Ready for QA" (that string comes straight from `bug.status`, unrelated to the routing fix). But no `@<name>` ownership line appeared anywhere, and no "נדרש לקבוע בעלים" fallback either — the new rule was silently dropped.

Root cause (template design, not the data/code): the instruction lived as item 3 of a 4-item numbered "הצעדים להיום" list, conditional on data that may or may not be present. Under the ~120–250 word length pressure, the model collapsed the list to items 1–2 (@אור/@דור) plus two generic items from what was written as item 4, skipping the conditional item 3 entirely.

Fix: moved it out of "הצעדים להיום" into its own standalone, explicitly mandatory section — "*ממתין ל-QA (לפי טיקט):*" — between "באגים פתוחים" and "הצעדים להיום", with an instruction that it must never be cut for brevity (cut "דגשים" detail instead). Bumped target length to 150–300 words to make room. This is a prompt-engineering fix only; no service-layer code changed (the `ready_for_qa` gap/ownerAction logic from the earlier change is untouched and still has its own passing unit tests).

Not yet re-verified against a live run — ask Alpir to re-run the agent after this deploys and confirm the new section appears.

## Fix: Ready for QA bug was double-counted under דור (2026-10-05)

Alpir flagged: a bug in Ready for QA should never show up as דור's action item, even if it's missing Assignee/Due — dev's part is done once a bug reaches QA, so ownership is only ever the ticket's QA/Reporter (or unassigned), never דור.

Root cause: `detectGaps` generated `open_bug_missing_assignee`/`open_bug_missing_due` (routed to `לדור`) for *any* open bug missing those fields, with no exception for Ready for QA — so a Ready for QA bug with no Due date could appear both under "@דור" and under the new "ממתין ל-QA" section.

Fix: both checks now skip a bug whose status matches Ready for QA. Added a test asserting a Ready-for-QA bug with empty assignee/due produces *only* the `ready_for_qa` gap, routed away from `לדור`. 32/32 tests pass (was 31), `tsc --noEmit` clean.
